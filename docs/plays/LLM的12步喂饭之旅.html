🎬 第四幕：合并成能看懂的样子
G
Graph
我现在做 7 件小事—— 1. 字段去重（多个关键词可能命中同一个字段） 2. 指标依赖的字段如果漏了，从元数据库补回来（GMV 依赖 `order_amount`） 3. ES 搜到的"华北"这个值，放回 `dim_region.province` 的 examples 里 4. 字段按表分组（`fact_order` 下的字段、`dim_region` 下的字段） 5. 每张表补齐主外键（JOIN 需要） 6. 精简字段，只留 LLM 需要的信息 7. 精简指标，同样只留必要信息 给你看看我合并完的样子：
- name: fact_order
  role: fact
  columns:
    - name: order_amount
      type: decimal(10,2)
      role: measure
      description: 订单金额
      alias: [销售额, 交易额]
    - name: region_id
      role: foreign_key
    - name: date_id
      role: foreign_key

- name: dim_region
  role: dimension
  columns:
    - name: province
      type: varchar(50)
      examples: [华北, 华东, 华南]
      description: 省份
    - name: region_id
      role: primary_key

指标：
- name: GMV
  description: 所有订单的成交金额总和
  relevant_columns: [fact_order.order_amount]
L
LLM

💡 为什么需要这步
💡 为什么需要这步三路召回的结果是零散的，不合并 LLM 无法理解。同时要补齐关联信息（主外键、指标依赖字段），否则 LLM 写 JOIN 时缺胳膊少腿。

FROM fact_order fo
JOIN dim_region dr ON fo.region_id = dr.region_id

哦对，我错了。`dim_date` 只有 `date_id`，没有 `year` 和 `quarter`。那我用 `YEAR()` 和 `QUARTER()` 函数吧。 修正：
SELECT SUM(fo.order_amount) AS GMV
FROM fact_order fo
JOIN dim_region dr ON fo.region_id = dr.region_id
JOIN dim_date dd ON fo.date_id = dd.date_id
WHERE dr.province = '华北'
  AND YEAR(dd.date_id) = 2025
  AND QUARTER(dd.date_id) = 1

💡 为什么需要这步LLM 不是数据库，它对字段名的记忆可能不准。EXPLAIN 校验 + 修正循环是最后一道防线。

谢幕总结

Graph 的步骤解决 LLM 的什么痛点
extract_keywords自然语言太模糊，需要先提炼检索线索
recall_column/value/metric我不知道数据库里有什么，需要你帮我搜
merge_retrieved_info零散的信息我理不清关系，需要你帮我整理好
filter_table/metric信息太多我处理不了，需要你帮我缩小范围
add_extra_context我需要知道当前时间、数据库类型才能写对语法
generate_sql这是我唯一真正"动脑"的步骤
validate_sql我可能记错字段名，需要你帮我检查
correct_sql错了你给我报错信息，我改
run_sql最终你去执行，我只看结果
✒ LLM 不是不能用，是不能裸奔用。把"理解数据库结构"这件难事拆成 12 步流水线，每步只让 LLM 处理它擅长的部分，最终它就只要在最后一幕动一次脑——写 SQL。
